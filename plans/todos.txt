plans/todos.txt — design findings not yet worth a PLAN
=======================================================

Seeds, not plans. Each is a finding with enough reasoning attached that writing
the PLAN later does not mean re-deriving it. When one graduates, it becomes
PLAN-{YYYYMMDD-HHMM}-{title}-todo.md per plans/README.md and its entry here is
deleted — not left behind as a second copy that drifts.

Raised 2026-08-25, from a review of the record model while drawing
demos/entity-map.html. Scope of that review: libpcomm/schema, core/records.hpp,
core/ids.hpp, pcomm-read/link_sql.hpp, the provider greps. NOT reviewed: the
hook layer, the recorder hot path, ui/, agent/. Nothing here is a bug report —
these are design questions, and a few may be answered "leave it alone".


1. DONE (2026-08-25): the Edge rule is written down
----------------------------------------------------------------------------
Was: "Edge has no producer and the rule for earning one was never written
down". The rule now lives in libpcomm/schema/README.md under "When a relation
earns an Edge", with a pointer from EdgePredicate in core/vocab.hpp.

Inline when 1:1, known at write time, and hot. Edge when 1:N, time-varying, or
LEARNED LATER — the last being a property of the format and not a preference,
since a stream is a packed array with no index and a field can never be filled
in afterwards.

Attribution stays. It is not dead code: records.hpp seeded one record of each
archetype so the writer and reader exercise all four paths, and each of the four
predicates was then correctly solved by an inline field or a reader-side join.
What remains are items 2, 3 and 4 below — the two inline fields the rule says
are already wrong, and the one prospective producer.

2. Inlining a relation asserts 1:1 and time-invariant. Managed memory is neither
-------------------------------------------------------------------------------
`mem_object.device` is one DeviceId set at allocation. cuMemAllocManaged funnels
into the same handle_alloc as cuMemAlloc (nvbit_backend.cu:1203), so a managed
allocation gets a single residency recorded once — and managed memory migrates
by definition. The field can only ever hold a point-in-time claim and there is
nowhere to put the migration.

ResidesOn + a Temporal is exactly the shape that fits. This is the strongest
argument that Edge should stay rather than be retired.

MEASURED 2026-08-26, and the answer is "latent, but not safely latent".

  - No first-party workload allocates managed memory. Grep over every source in
    tests/hpc/ and bench/ for cudaMallocManaged / cuMemAllocManaged /
    cudaMemAdvise / cudaMemPrefetchAsync: zero hits.
  - The libraries can. MN5 login-node ELF sweep of the 26.5 stack: libnccl
    .so.2.29.3 and libnvshmem_host.so.3.6.5 each carry `cuMemAllocManaged` and
    `cudaMallocManaged` as runtime-resolved STRINGS with no undefined symbol —
    i.e. reached through cuGetProcAddress, the door dmabuf_registry.hpp already
    hooks. libucp carries neither. So the door is open in exactly the two
    libraries our corpus runs, and closed in the third.
  - `handle_alloc` records `cudaGetDevice()` — the CURRENT device, not where the
    memory lives. For a managed allocation that is not merely a point-in-time
    claim, it is a claim about the wrong thing entirely.
  - pcomm itself allocates managed memory: `cudaMallocManaged(&state->
    channel_dev, ...)` in nvbit_at_ctx_init (nvbit_backend.cu:1292). It is not
    self-recorded, but only because NVBit suppresses callbacks for calls made
    from inside a callback — the same unwritten property handle_alloc's own
    cudaGetDevice relies on (the comment at :417 says so). Nothing asserts it.

So this stays latent while the corpus is what it is, and the corpus is about to
change. QuantumESPRESSO built with the NVIDIA HPC SDK uses CUDA Fortran managed
arrays, and LAMMPS/Kokkos has a CudaUVM backend — both are on the real-app list
agreed 2026-08-26, and either would make this live on its first capture.

WHAT IS MISSING BEFORE THAT IS A DISCRIMINATOR. Today a managed allocation and a
device allocation are byte-identical in `mem_object`: nothing records which door
the allocation came through, so we could not tell a live case from a latent one
even while looking at it. That is the same shape as item 11's `pd` — a fact the
capture carries and cannot name. Recording the door is a smaller change than
ResidesOn and is a prerequisite for knowing whether ResidesOn is needed; it also
wants a hash bump, so it pairs with item 7r.


3. source_line is 1:1 pc -> line; inlined device functions are 1:N
------------------------------------------------------------------
One source_line row per pc. With -lineinfo and inlined __device__ functions, a
pc corresponds to a CHAIN of (file, line) frames, and the record can hold only
one of them — with nothing saying which end it is.

PARTLY ANSWERED (2026-08-25, du04). "source_line is empty in every harvested
capture" is no longer true: the p2p_kernel capture carries 2 rows, both
p2p_kernel.cu:30, for two distinct pcs. So nvbit_get_line_info does return
locations, and on this workload it returns ONE frame per pc — two pcs mapping to
one line, not one pc mapping to several. That is consistent with the record's
1:1 shape and is NOT evidence either way about inline chains, because
p2p_kernel.cu has no inlined __device__ call to produce one. A workload that
does is what would settle it.

4. The NCCL unattributed-access gap is Edge-shaped
--------------------------------------------------
PLAN-20260817-0705 is blocked on naming an allocation the application never
made: 1,179,948 accesses on case 05 land in no tracked object, because NCCL's
internal channel buffers arrive through a door gpumem does not record.

Whatever eventually names them will do so LATER, and from a different component
than the one that recorded the access. An inline field cannot serve that by
construction — the field is written when the access is. An Edge can: subject =
the address band or access, object = the allocation, pred = TouchedObject,
emitted by whoever learns it, whenever they learn it.

This does not unblock the plan — the blocker is still "there is nothing to join
on". It says that when the blocker lifts, the record to carry it already exists.


5. DONE (2026-08-25): the five lifetime-less Entities are Artifacts
-------------------------------------------------------------------
node_identity 524, ib_qp_signalling 126, ucx_worker_address 622,
ucx_ep_connection 624 and nccl_dev_comm 910 are RecordKind::Artifact. Option (b),
as the project's own preference dictated: take the better schema, re-run the
corpus.

The test, written down in libpcomm/schema/README.md under "The archetypes are a
test, not a label": does anything ever close it? If no close path exists and
none is missing, it is not an Entity.

ONE THING THIS TURNED UP THAT WAS WORTH MORE THAN THE CHANGE. Reclassifying moves
no layout, no size and no field, so the stride check cannot see it — and the
SCHEMA HASH DOES NOT MOVE EITHER, because a record's kind lives in a pcomm.fbs
comment rather than a declaration. Every stream header has carried `kind` since
format 1 and nothing ever read it, so the reclassification would have been
silent: old captures reading clean under the wrong archetype. stream_header_error
validates `kind` now, and stream_format.cpp has the refusal case. That hole
existed independently of this change and would have stayed open.

Captures predating 2026-08-25 holding any of those five records are refused by
name and must be re-captured.

6. DONE (2026-08-25): entity_close's opener list is no longer enumerated
------------------------------------------------------------------------
The comment named four openers and was stale by twelve — sixteen record types

7. SETTLED (2026-08-25, du04): the stamp is load-bearing — keep it
-------------------------------------------------------------------
Measured on hardware, which is what this entry asked for. du04, CUDA 13.0,
driver 580, 4x A100, case 03's p2p_kernel rebuilt for sm_80, pcomm at 2a3f41d:

    gpu_access rows                16384
    launch = 0, cannot join         4096   25.0%
    joins a gpu_kernel span        12288   75.0%

So the record's own Temporal is the ONLY timing a quarter of the firehose has.
Removing it would leave those rows unplaceable on the timeline. The 48 bytes
stay. Question closed.

What the measurement actually found is in the commit beside it: the 25% was a
DEFECT, not a property. g_grid_launch_id started at 0, so the first launch of
every process minted a real id equal to the sentinel both fields document as
"unknown", and the reader's join could never match it. Starting at 1 took the
same capture to 0.0% unjoinable, 4/4 kernels. The share was 1/N for an N-kernel
run — small on long runs, never zero, and silent.

The packing observation from the previous version of this entry still stands and
is now the only live part: Temporal is 48 bytes carrying 29 bytes of content, of
which `value` (8 B) is meaningful only for TimeKind::Counter, which nothing
emits. That is a separate change, wants a hash bump, and is the same decision as
item 11's "Counter has no producer".

8. DONE (2026-08-25): the derived tables declare their columns
---------------------------------------------------------------
Every kTables entry in pcomm-read/link_sql.hpp now carries a `columns` line —
the columns it promises, in order — and link::columns_match checks it against
what the SQL really produces. Renaming a column is loud now instead of blanking
a panel.

Checked on BOTH paths, which is the part that took a second try. It asks the
SQL, not the catalog: `pcomm ui` defines the layer as views so a relation
exists, but `pcomm link` COPYs each entry straight to Parquet and never CREATEs
one, so a catalog lookup checked nothing on exactly the path that writes the
fixture everything else reads. link_health fell into that same trap once — the
comment beside it in main.cpp records it.

Not a schema. A schema for these is still the larger job (types, nullability, a
version), and the README's "what is still not covered" section still stands. But
the names are pinned, which was the part that could silently rot.

9a. The original finding
------------------------
wr_flow, timeline_span and link_health have off-cluster ctests built from
synthetic CSVs (flow_pairing_agree.sh, wr_flow_rule.sh). Those are the best
tests in the tree — wr_flow_rule.sh exists because deleting a rule clause left
the other one green TWICE.

comm_edges and object_access — the two tables behind the headline panels — have
ZERO local tests and are verifiable only on MN5, where the queue is slow and a
red board has more than once been the harness rather than the tracer.

The fixture pattern already exists and is pointed at the least-consumed tables.
Point it at the most-consumed ones. Probably the highest value-per-hour item in
this file.


10. DONE (2026-08-26): the vendor-free rule is checked, and it is narrower
--------------------------------------------------------------------------
`tools/check_vendor_free.py`, ctest `vendor_free`. libpcomm was already clean;
what the check did was force the rule to be stated precisely enough to run.

IT CANNOT BE A GREP. Vendor names are on nearly every page of libpcomm — in
COMMENTS, which is where this codebase keeps its reasoning, and in dlsym string
literals, which is HOW core stays vendor-free. A check over raw text flags all
of those, and a check nobody can keep green gets deleted. So it strips comments
and string literals first and judges what is left.

THE RULE IS TYPES AND HEADERS, NOT NAMES. Core may name a vendor symbol, because
interposition and dlsym work by name and need no header: engine.cpp defines five
`extern "C"` doors — nvshmem_malloc/calloc/align/free and ibv_destroy_qp — whose
signatures are `void*` and `size_t` throughout, and engine_abi.h already records
why the QP close door can belong to neither provider. Those are allowlisted BY
NAME in the script, so a sixth door drifting into core has to be written down;
that is the layering violation worth catching, and it was invisible before.

The two files nearest the line pass, and how is the rule in miniature:
mem_attr.hpp declares libcuda's signature itself instead of including cuda.h,
dmabuf_registry.hpp copies CUresult's ABI under the name `CuResult`. Twelve
mutations were used to check each rule can fail and each exemption can not;
removing one allowlist entry turns engine.cpp red, so the list is load-bearing.

WHAT IT STILL CANNOT CHECK, and this half of the original finding stands:
core/mem_attr.hpp hardcodes kAttrDeviceOrdinal = 9 — a vendor ABI constant with
no vendor type in sight. Its own comment records that a wrong constant (4,
CU_POINTER_ATTRIBUTE_HOST_POINTER) survived a provider's entire lifetime because
every failure mode of device_of looks like kUnknownDevice. No regex can check a
magic number against a header it is forbidden to include. That is the same
ambiguity PLAN-20260817-0634 is about, and it is where the residue lives.


11. Known and already written down, listed so they are not re-derived
---------------------------------------------------------------------
  - pd is carried by four ibverbs entities and created by no record. A query can
    group by it and never name it.
  - The versioning machinery has no production user; the only exercise is a demo
    family at ids 900+ inside record_versioning.cpp. First real bump is where the
    convention meets a provider that must emit both versions.
  - Range-containment object identity is sound only within a lifetime, and
    lifetimes are only sometimes recorded (records.hpp says so).
  - Three id ranges are allocated and empty: cupti 300-399, libfabric 400-499,
    ucx_deep 800-899.


12. DONE (2026-08-25): the figures are checked against the declarations
------------------------------------------------------------------------
tools/check_figures.py, registered as ctest `figures_current`. Three lists
checked against each other: the PCOMM_RECORD declarations (source of truth,
parsed with schema_check.py's own parser), gen_figures.DRAWN (what the diagrams
drew), and gen_figures.FAMILIES (what the index table lists). Catches a record
that exists and is not drawn, one drawn and not declared, and a type_id or
archetype that disagrees.

The layout still is not derived from anything, and should not be — a figure is
an argument about which relationships matter. Only the SET is checked.

Worth remembering: it executes gen_figures.py from source instead of importing
it, because Python validates a cached .pyc on (mtime, size) at one-second
granularity — so a same-length edit in the same second reuses stale bytecode.
That fooled this check during its own mutation test, which is how it was found.
